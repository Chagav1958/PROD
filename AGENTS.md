## Кодировка — проверять ПЕРЕД любой записью

| Тип файла | Кодировка | BOM | Последствия ошибки |
|-----------|-----------|-----|-------------------|
| `.ps1` | UTF-8 | **с BOM** | PS 5.1 читает как CP1251 → кракозябры/ошибки |
| `.json` / `.jsonc` | UTF-8 | **без BOM** | Bug-044: OpenCode не грузит плагины |
| `.sql` | Windows-1251 | нет | ANSI |
| `.bat` | Windows-1251 | нет | ANSI |
| `.md` | UTF-8 | без BOM | Документация |

Исправление BOM: `scripts\Remove-BomFromConfigs.ps1`

## Запуск PowerShell из bash tool

```
ВСЕГДА:      powershell -NoLogo [-File script.ps1]
НИКОГДА:     -NoProfile (Bug-046: ломает UTF-8 вывод)
```

## РАСПОЗНАВАНИЕ СОКРАЩЕНИЙ

- **Исключения** (общеизвестные технические термины, НЕ сокращения проекта — расшифровка не нужна): Jira, SQL, API, JSON, MCP, LLM, PB, VSS, RFC, ASE, SYBASE, GUI, PBL, PBT, PS, BOM, CP1251, UTF8, WPF, DLL.
- **Частые сокращения проекта:** ОП (операция в GUI), ДО (диалоговое окно сервиса), СОХР (архив проекта), СОКР (показать сокращения), СОХРАИС/SAVEAIS (сохранить знания о проекте в ais-catalog), СОХРПРОД/SAVEPROD (сохранить знания о работе в OpenCode в opencode-mcp), РР/РР (принудительно русский), ОО (продолжить/проверить todowrite), ОБР/OUT (анализ вывода), ОТЧЁТ (открыть отчёт), ЦИКЛ N (автоисправление ОП N), TASK (начать задачу), DLLM (окно LLM), МОРДА (главное окно GUI), ПБ (прогресс-бар), СВЕЖPB/NEWPB и СВЕЖSQL/NEWSQL (самый свежий объект из Ready_*), OLDPB/OLDSQL (исходный из Git_*), СТАНДАРТ1, ПРОМПТ, НОМ (номер ОП), ЗАПОМНИ (запомнить правило), FIXSHOW, MSG (MessageBox), СТАРТ (preflight), FIX/EDIT N, TODOWRITE, SYS (системная задача Jira), Golden (основная БД), STELLS (скрытие консоли PS чистыми методами .NET — антивирус не детектит), ПРОДОБР (продолжить обработку по утверждённому плану).

## Правило TASK
`TASK <имя_задачи> [<папка>]`

0. **Определение корневого пути задачи:**
   - `SYBASE-*` / `SUPRT-*` → `C:\AIS\1 Release`
   - Все остальные задачи → `C:\AIS\AI\Prod\tasks`
   - Если указан явный `<папка>` — использовать его (переопределяет автоопределение).

0a. **Поиск папки задачи (ОБЯЗАТЕЛЬНО, применять при ЛЮБОМ упоминании SYBASE-*/SUPRT-*, включая остановку/продолжение):**
   - Сначала искать папку, **начинающуюся** с имени задачи + суффикс: `<имя_задачи>_*` (напр. `SYBASE-19371_19365`).
   - Если такая папка **есть** — работать в ней, новую НЕ создавать.
   - Папку с точным именем `<имя_задачи>` создавать/использовать **только если** папки с префиксом нет.
   - Суффикс `_<число>` после имени = ключ **родительской** задачи, в ней описание ТЗ (напр. `_19365` = SYBASE-19365). Или `_ТЗ`.

**Правило именования папок для подзадач:**
   - Если ТЗ (техническое задание) создаётся в **родительской** задаче (напр. `SYBASE-19365`), а не в самой задаче (`SYBASE-19371`), то папка именуется `<дочерняя_задача>_<родительская_задача>` → `SYBASE-19371_19365`.
   - Имя родительской задачи определяется по Jira: задача, в описании которой находится ТЗ для текущей задачи.
   - Папка `SYBASE-19371` (без суффикса) может существовать как "пустышка", но рабочая папка — с суффиксом родительской задачи.
1. Создать/проверить папку задачи по корневому пути (п.0): сначала `<имя_задачи>_*` (см. п.0a), иначе `<имя_задачи>` или `<имя_задачи>_ТЗ`
2. **Авто-выгрузка оригиналов** в `Git_YYYY_MM_DD`:
   - SQL: выгрузить из `dev_golden` через `SQL_exp_single.bat` (для каждого объекта)
   - PB: скопировать из `PB_Current\<lib>\` или `C:\SRC125\gold\<lib>\`
   - Если список объектов неизвестен — запросить у пользователя или прочитать из Jira
3. `Test_YYYY_MM_DD` — изменённые объекты (выгружать сразу после разработки). **Сюда попадают объекты, доработанные как через LLM, так и вручную в PB IDE.** Ручные правки — просто скопировать файлы в папку.
4. `Ready_YYYY_MM_DD` — готовые (**только по команде после тестирования!**)
5. `Describe\<объект>.txt` — описания изменений (создать для каждого объекта)

**Смешанная работа (LLM + вручную):** часть объектов может дорабатываться в PB IDE без участия LLM. Такие объекты вручную копируются в `Test_` и `Describe\`. ОТЧЁТ и вывод в ПРОД обрабатывают ВСЕ объекты одинаково, независимо от способа доработки.

## Работа с TaskPlan — детальное руководство

> **Полное руководство с примерами:** `docs\taskplan-gui-guide.md` (и `.html`, `.pdf`)

TaskPlan — сервис управления объёмными задачами через ДО (Show-TaskPlanGUI.ps1), трекер (TaskPlan-Tracker.ps1) и диспетчер (TaskPlan-Manager.ps1).

### Запуск GUI
- Команда `TaskPl` → запускает `Show-TaskPlanGUI.ps1` (скрытое консольное окно, WPF ДО)
- Альтернатива: `powershell -NoLogo -File scripts\Show-TaskPlanGUI.ps1 -TaskName <имя>`

### Вкладки ДО
1. **Список задач** — таблица этапов с цветовой маркировкой: зелёный `[x] готово`, жёлтый `[~] в работе`, красный `[!] отложено`, серый `[ ] не начато`. Показывает прогресс-бар и статистику.
2. **Управление** — поля для создания и изменения плана:
   - **Имя задачи** — ComboBox с историей из `task_index.json` (можно ввести новое)
   - **Корень задач** — `C:\AIS\1 Release` (SYBASE-/SUPRT-) или `C:\AIS\AI\Prod\tasks` (остальные)
   - **Цель (Goal)** — текстовое описание задачи
   - **Этапы** — многострочное поле, формат `Текст этапа` или `Текст|Исполнитель`
   - **LLM / исполнитель** — ComboBox: бесплатные сначала (deepseek-v3, llama-3-70b, gpt-4o-mini...), затем платные, затем «(своё)»
   - **Статус этапа** — ComboBox: `не начато`, `в работе`, `готово`, `отложено` (русские названия, внутри маппятся на todo/wip/done/defer)
   - **Номер этапа** — 1-based
   - Кнопки: Новый план, Уст. статус, Доб. этапы, След. этап, Подг. бриф, Синхр. JSON
3. **Тесты** — запуск полного цикла автотестов `TaskPlan-Tests.ps1` (15 тестов: создание, чтение, статусы, этапы, бриф, GUI Automation)

### Создание задачи через ДО
1. Ввести имя задачи (напр. `SYBASE-12345` или `TASK-1`)
2. Указать Goal
3. Заполнить этапы (каждый с новой строки)
4. Нажать **«Новый план»** — создаётся:
   - Папка задачи (`Describe\`, `Git_YYYY_MM_DD`, `Test_YYYY_MM_DD`)
   - `ПЛАН_РЕАЛИЗАЦИИ.txt` с чек-боксами
   - `plan_state.json` — зеркало для ДО-индикатора

### Управление этапами
- **Уст. статус** — изменить статус этапа по номеру (с маппингом рус→англ)
- **След. этап** — найти первый неготовый этап и вывести его номер
- **Подг. бриф** — подготовка брифа для дорогой LLM (требует [!]-этапа)
- **Синхр. JSON** — пересобрать `plan_state.json` из `ПЛАН_РЕАЛИЗАЦИИ.txt`

### Диспетчер задач (TaskPlan-Manager.ps1 + task_index.json)
- `TaskPlan-Manager.ps1` — консольный менеджер множества задач
- Хранит `task_index.json` в корне задач: список задач с полями `id`, `name`, `prompt`, `clarifications`, `status`, `created`, `updated`
- Поддерживает: `create`, `list`, `show`, `switch`, `suspend`, `resume`, `edit-prompt`, `delete`
- **Текущая задача** (`current`) — одна активная, остальные `paused` при переключении
- При `switch` — старая задача автоматически `paused`, новая `active`

### Автотесты
- `TaskPlan-Tests.ps1` — полный цикл без участия человека
- 15 тестов: трекер (создание, чтение, статусы, next, add, sync, show, brief) + GUI (запуск, поиск окна, закрытие)
- Запуск из вкладки «Тесты» или вручную: `powershell -NoLogo -File scripts\TaskPlan-Tests.ps1`

### Скрытые вызовы (трекер напрямую)
- `TaskPlan-Tracker.ps1` — ядро логики, работает с `ПЛАН_РЕАЛИЗАЦИИ.txt` и `plan_state.json`
- Параметры: `-Action` (new|add|set|show|next|sync), `-TaskName`, `-Stages[]`, `-StageNum`, `-Status` (todo|wip|done|defer), `-DoneBy`, `-Goal`, `-ReleaseRoot`, `-Force`
- Вызов извне: `& scripts\TaskPlan-Tracker.ps1 -Action new -TaskName X -Goal "..." -Stages @("S1","S2") -Force`

### OUTPL — анализ и автоисправление ошибок TaskPlan
Все скрипты TaskPlan (трекер, тесты, GUI) пишут события и ошибки в единый лог `temp\taskplan_last_output.log` через `TaskPlan-Logger.ps1`.
Команда `OUTPL` запускает `Out-TaskPlan.ps1`, который:
- Читает лог и распознаёт 8 типов ошибок (TASK_PATH_ERROR, TRACKER_MISSING_PLAN, TRACKER_JSON_ERROR, GUI_LAUNCH_FAIL, GUI_AUTOMATION_FAIL, PS51_SYNTAX_ERROR, TEST_FAILURE, LOGGER_MISSING)
- Выдаёт диагностику `[ERROR]+[FIX]` по каждому типу
- С флагом `-AutoFix` убивает зависшие GUI-процессы
- Сохраняет отчёт в `temp\taskplan_outpl_report.txt`
- Запуск: `powershell -NoLogo -File scripts\Out-TaskPlan.ps1 [-AutoFix]`

**Fix Cycle (цикл автоисправления):**
- `Out-TaskPlan-FixCycle.ps1` — аналог `auto_fix_loop` для TaskPlan
- Параметры: `-RunTests`, `-RunTracker`, `-RunGUI`, `-MaxIter N`, `-TaskName <имя>`
- Цикл: выполнить операцию → OUTPL анализ → автоисправление → повтор

**Автотесты OUTPL:**
- `Out-TaskPlan-Tests.ps1` — 10 тестов (логгер 2, OUTPL 5, Fix Cycle 3)
- Запуск: `powershell -NoLogo -File scripts\Out-TaskPlan-Tests.ps1`

## Правило остановки/продолжения работы по задаче
Применять для любой долгой задачи (SYBASE-*/SUPRT-*/иная), чтобы работу могла продолжить любая LLM-сессия.

**Остановка (по команде пользователя или при неясности дальнейших шагов):**
- Не продолжать самостоятельно, если следующий шаг требует решения аналитика (выбор варианта, сверка постановки).
- Сохранить всё по правилу Knowledge First: MCP `ais-catalog_save_knowledge` (анализ, вывод, карта воздействия, **точка возобновления** с командой продолжения) + бизнес-правило `ais-catalog_add_business_rule`.
- Файлы задачи в папке `Describe\` (анализ + ПЛАН_РЕАЛИЗАЦИИ.txt).
- Статический якорь: запись в `rules/pending-tasks.md` (видна без MCP).
- Продолжение допускается **ТОЛЬКО по явной команде** пользователя (напр. «продолжить SYBASE-19371»). Автопродолжение запрещено.

**Возобновление (по команде):**
1. Knowledge First: `ais-catalog_search_knowledge("<имя_задачи>")` → поднять знания + `get_business_rules`.
2. Прочитать `Describe\` папки задачи (см. поиск папки в правиле TASK, п.0).
3. Продолжить с раздела «СЛЕДУЮЩИЙ ШАГ» в ПЛАН_РЕАЛИЗАЦИИ.txt.
4. При смене папки (напр. на `<имя>_*`): перенести все файлы задачи в правильную папку, обновить ссылки в `pending-tasks.md` и MCP, удалить ошибочную папку.

## Стратегия решения объёмных задач недорогими LLM

Цель: решать большие задачи дешёвыми/бесплатными LLM, переключаясь между ними по мере исчерпания ресурса, а дорогие мощные LLM запускать точечно — только на подзадачи, непосильные дешёвым, и после максимальной подготовки (чтобы дорогая LLM тратила минимум токенов).

### 1. Классификация задачи (в начале обработки)
Задача = **короткая** или **объёмная**. Признаки объёмной (достаточно ЛЮБОГО):
- пользователь назвал её задачей / дал имя (`TASK <имя>`, ключ SYBASE-*/SUPRT-*);
- ожидается > 3 самостоятельных этапов (порог шагов);
- затрагивает > 3 объектов PB/SQL или несколько папок (порог объектов).

- **Короткая** → решается сразу, БЕЗ имени и плана (обычный ответ).
- **Объёмная** → создать уникальное имя задачи (по правилу TASK, п.0) и ОБЩИЙ ПЛАН. Далее работать только по плану.

### 2. Общий план (ПЛАН_РЕАЛИЗАЦИИ.txt в папке задачи, Describe\)
Обязательные разделы:
- ЦЕЛЬ, статус (в работе / отложено / завершено);
- ЭТАПЫ — нумерованный список с чек-боксами: `[ ]` не начат, `[~]` в работе, `[x]` готов, `[!]` отложен на дорогую LLM;
- у каждого этапа: краткий результат + отметка «кем/какой LLM выполнен»;
- СЛЕДУЮЩИЙ ШАГ — с чего продолжить;
- ОЧЕРЕДЬ ДОРОГИХ ПОДЗАДАЧ — список `[!]`-этапов с обоснованием «зачем нужна мощная LLM».
Дубли статуса плана: MCP `ais-catalog_save_knowledge` (сводная запись) + якорь в `rules/pending-tasks.md`. Синхронно с `todowrite` в текущей сессии.

### 3. Поэтапное выполнение с фиксацией
- Перед этапом: пометить `[~]`, синхронизировать `todowrite`.
- После этапа: пометить `[x]`, записать результат в план + `Describe\<объект>.txt`, обновить сводную запись MCP (НЕ дробить — см. «Дисциплина записей MCP»).
- Фиксация после КАЖДОГО этапа — чтобы любая следующая LLM продолжила без потерь.

### 4. Переход на другую (дешёвую) LLM при исчерпании ресурса
Признаки исчерпания: ошибки `Insufficient balance`, лимит контекста, деградация ответов.
Порядок:
1. Немедленно зафиксировать текущий этап (`[~]`→ результат + СЛЕДУЮЩИЙ ШАГ) в плане, MCP, `pending-tasks.md`.
2. Не начинать новый этап на исчерпанном ресурсе.
3. Новая LLM возобновляет по правилу «Возобновление»: Knowledge First → план → продолжить с СЛЕДУЮЩЕГО ШАГА. Автопродолжение запрещено — только по команде «продолжить <имя>».

### 5. Откладывание непосильных подзадач на дорогую LLM
Если этап непосилен текущей дешёвой LLM (сложный рефакторинг, глубокий анализ, тонкая логика):
- пометить этап `[!]`, вынести в ОЧЕРЕДЬ ДОРОГИХ ПОДЗАДАЧ;
- создать спец-подзадачу (имя `<имя>_SUB_<n>` или отдельная папка), указать ЗАЧЕМ нужна мощная LLM (что именно дешёвая не тянет);
- НЕ запускать дорогую LLM сразу — сначала максимально подготовить (см. п.6).

### 6. Подготовка ПЕРЕД запуском дорогой LLM (экономия токенов)
Дешёвая LLM обязана выполнить всё возможное, чтобы дорогая тратила минимум:
- собрать и приложить точный контекст: нужные фрагменты кода (не целые файлы), карту зависимостей, релевантные знания MCP;
- сузить задачу до конкретного вопроса/объекта, убрать лишнее;
- сформулировать ожидаемый результат и критерий приёмки;
- выполнить черновой/частичный вариант, если возможно (дорогой LLM — только доводка);
- приложить границы и известные ограничения.
Готовый «пакет для дорогой LLM» сохранить в `Describe\<имя>_SUB_<n>_бриф.txt`.

### 7. Роутинг по стоимости (принцип)
- Основная обработка по плану → дешёвая/бесплатная LLM.
- Дорогая мощная LLM (напр. Opus) → ТОЛЬКО этапы `[!]` и только с готовым брифом (п.6).
- Бюджет дорогой LLM беречь: при использовании Opus держать баланс в допустимых пределах (падение ниже порога → `Insufficient balance`). Модель выбирается через `DLLM`.

### 8. Роль ДО (диалогового окна GUI) — для будущей реализации
Функционал (когда будет разрабатываться кодом) должен на ДО: показывать общий план и движение по этапам (`[ ]/[~]/[x]/[!]`); указывать, для чего нужна дорогая LLM (очередь подзадач); запускать продолжение общей обработки на новой LLM; запускать решение `[!]`-подзадач на дорогой LLM. На этом этапе — только стратегия/правила; код (планировщик, трекер этапов на ДО, автопереключение LLM) реализуется отдельно после утверждения стратегии.

## Правило сохранения знаний (куда и что)

**Решает модель автоматически**, без запроса пользователю. При вызове `save_knowledge`:

| Сервер | Что сохранять | Примеры |
|--------|---------------|---------|
| **`ais-catalog`** | Всё о корпоративном проекте: объекты PB/SQL, бизнес-логика, связи, сленг аналитиков, особенности обработки данных, задачи (SYBASE-*/SUPRT-*) | `usp_report_list_multi_m`, логика PROD, «ДО», `u_report_list.sru`, `golden_commission` |
| **`opencode-mcp`** | Всё об OpenCode как инструменте: скрипты PS, ДО, настройка провайдеров, MCP-серверы, ошибки jsonc, ПБ, ОТЧЁТ, шаблоны | RouterAI setup, шаблон MCP, WPF handler scope, Bug-046, СОХРМСР |
| **`rules-mcp`** | **НИКОГДА не сохранять** — читает файлы правил напрямую | Кодировки, сокращения, баги — авто из `.mdc`/`.md` |
| **`sybase-docs`** | **НИКОГДА не сохранять** — документация ASE/PB, только чтение | — |
| **`atlassian`** | **НИКОГДА не сохранять** — Jira/Confluence, только чтение | — |

### Как модель принимает решение
1. Текст про PB, SQL, задачу Jira, бизнес-правило, структуру БД, объект AIS → **`ais-catalog`**
2. Текст про OpenCode, PowerShell, .ps1, opencode.jsonc, MCP, ДО, WPF, модели, провайдеры → **`opencode-mcp`**
3. Пограничный случай → **`ais-catalog`** (приоритет проекта)

### Дисциплина записей MCP (эффективность поиска)
При сохранении знаний через `save_knowledge` соблюдать:
- **Писать СВОДНУЮ запись, не дробить.** Одна запись на задачу/объект со структурой (анализ → вывод → карта воздействия → точка возобновления), а не 4-5 частичных. Дробные записи раздувают контекст и вытесняют друг друга из топа при `search_knowledge(limit=5)`. (Пример исправления: SYBASE-19371 был разбит на id 164-168, слит в единую id 169.)
- **Явные теги** (SYBASE-19371, v_rule_dim_dictionary, rule_dimension) — они работают точнее FTS-поиска по русскому тексту (SQLite FTS5 не знает русской морфологии: запрос «правило» не найдёт запись с «правила»).
- **Проверять дубли перед сохранением.** Не создавать повторяющиеся записи (по тексту/тегам) и не дублировать `object_metadata` по (name, src).
- **Профилактика БД** (раз в месяц или после серии правок): бэкап `knowledge.db` → удаление дублей знаний → `VACUUM` → проверка `integrity_check` и orphan FTS (`SELECT COUNT(*) FROM knowledge_fts WHERE rowid NOT IN (SELECT id FROM knowledge)` должно быть 0). Orphan-строки в FTS свидетельствуют о неполном удалении.

**Критерий выбора:** если правило должны знать ВСЕ будущие сессии → **файл**. Если это опыт конкретной ситуации → **MCP-знание**.

## Правило документации — тройной формат (md + html + pdf)

**ВСЕГДА** при создании или обновлении документации `.md` одновременно формировать `.html` и `.pdf`:

| Требование | Значение |
|-----------|----------|
| **Язык** | Только русский, подробно, без сокращений (кроме общепринятых: Jira, SQL, JSON и т.п.) |
| **Фон** | Белый (`#FFFFFF`) или светло-серый (`#F5F7FA`), **НИКОГДА** чёрный |
| **Цвет текста** | Тёмный (`#1A3A60`, `#2D3748`, `#1A202C`), **НИКОГДА** серый или блеклый (`#A0AEC0`, `#CBD5E0`) |
| **Латиница** | Минимум — только технические идентификаторы (`opencode.jsonc`, `usp_`, `w_`). Весь пояснительный текст — кириллица |
| **Шрифт** | Системный с поддержкой кириллицы (`Segoe UI`, `Arial`, `Calibri`) |
| **Заголовки** | Жирные, крупные, контрастные |
| **Таблицы** | Границы чёткие, строки чередуются белый / `#F5F7FA` |

**Автоматизация:**
- Скрипт `scripts\Convert-Docs.ps1` — конвертация `docs\*.md` → `docs\*.html` + `docs\*.pdf`
- Запуск: `powershell -NoLogo -File scripts\Convert-Docs.ps1`
- HTML — inline CSS, белый фон, тёмный текст, полные русские названия
- PDF — через Edge/Chrome headless или IE COM ( fallback )

## Антивирус (Kaspersky + Defender) — Bug-063/064/065

**Причина удаления файлов:** Kaspersky Endpoint Security детектит PowerShell-скрипты с COM/OLE (Outlook), скрытый запуск, `-ExecutionPolicy Bypass`, отсутствие BOM. Зафиксировано МАССОВОЕ удаление 23.07.2026 (70+ файлов, включая OpenCode.exe с детектом PDM:Trojan).

**MCP знание:** id=84 (opencode-mcp), id=188 (ais-catalog).

**Пре-флайт ПЕРЕД записью .ps1:**
```powershell
# После создания/редактирования .ps1:
powershell -NoLogo -File C:\AIS\AI\Prod\scripts\Add-Bom.ps1
# Или для всех .ps1 в проекте:
powershell -NoLogo -File C:\AIS\AI\Prod\scripts\Preflight-Antivirus.ps1 -AutoFix
# Конвертировать критичный .ps1 в .bat-лаунчер (если AV продолжает удалять):
powershell -NoLogo -File C:\AIS\AI\Prod\scripts\ConvertTo-BatLauncher.ps1 "<путь-к-ps1>"
```

**СТАНДАРТ: .bat-лаунчер с base64** (если AV удаляет .ps1 — единственный надёжный способ)
- Конвертер `ConvertTo-BatLauncher.ps1` создаёт .bat с base64-кодированным .ps1
- В .bat НЕТ .ps1 на диске → AV не может детектить как PowerShell-скрипт
- Созданные .bat: Add-Bom, Fix-HexEncoding, Preflight-Antivirus, Init-Task, TaskPlan-*, Show-TaskPlanGUI, Out-TaskPlan, Export-PB, Compare-*, Add-ReleaseComment, Save-*, AIS_export, ConvertTo-BatLauncher, Show-TimeFIX, Prod-GUI

| Запрещённый паттерн | Замена |
|---------------------|--------|
| `-ExecutionPolicy Bypass` | `-ExecutionPolicy RemoteSigned` |
| VBS: `WScript.Shell.Run ..., 0, False` (скрыто) | `Shell.Application.ShellExecute ..., "open", 1` (нормально) |
| `[Runtime.InteropServices.Marshal]::GetActiveObject` | `New-Object -ComObject` (с проверкой `Get-Process`) |
| `IEX` / `Invoke-Expression` от подозрительных строк | Избегать; использовать .NET методы |
| `WindowStyle Hidden` | `WindowStyle Normal` или не указывать |
| Запись .ps1 без BOM | Всегда UTF-8 with BOM (первые 3 байта EF BB BF) |

**Как работать (ОБЯЗАТЕЛЬНО):**
1. **ПЕРЕД записью .ps1** — продумать паттерны, не использовать запрещённые
2. **Сразу ПОСЛЕ записи .ps1** — запустить `scripts\Add-Bom.ps1 <файл>`
3. **При массовых правках** — `Preflight-Antivirus.ps1 -AutoFix` (все файлы)
4. VBS-обёртки — только `Shell.Application.ShellExecute ..., "open", 1`
5. Рекомендовать добавить `C:\AIS\AI\Prod\` в исключения антивируса

**Утилиты:**
- `scripts\Add-Bom.ps1 <файл>` — добавление BOM к одному файлу
- `scripts\Preflight-Antivirus.ps1 [-AutoFix]` — массовая проверка + авто-фикс BOM
- `scripts\Fix-HexEncoding.ps1 <папка> -Recurse` — убрать HEX-экранирование

**Если файл удалён антивирусом:**
1. Проверить: `powershell -NoLogo -File C:\AIS\AI\Prod\scripts\Preflight-Antivirus.ps1 -AutoFix`
2. Проверить нет ли запрещённых паттернов
3. Пересоздать без опасных паттернов + Add-Bom.ps1
4. Если не помогает — добавить в исключения антивируса

- **`AGENTS.md`** (этот файл) — только ядро, без дублирования `.mdc`
