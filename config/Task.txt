Цель - подготовка и проверка объектов PowerBuilder 12.5 и SQL Sybase ASE 15.5  к выводу в промышленную эксплуатацию
## Методика и план подготовки и проверки объектов к выводу в промышленную эксплуатацию

### Основные понятия и структура хранения

| Логическое имя | Физическое расположение | Содержимое |
|---------------|--------------------------|------------|
| **Current** (рабочая версия) | `C:\Work` | Разрабатываемые исходные тексты PowerBuilder |
| **Main** (эталонная версия) | `C:\SRC125` | Исходные тексты PowerBuilder, синхронизированные с VSS |
| **БД Current** | Сервер A1, БД B | Разрабатываемые объекты SQL |
| **БД Main** | Сервер A2, БД B | Объекты SQL в промышленной эксплуатации |
| **Export_Current_PB** | Указан в bat/ps1 | Выгруженные тексты объектов PB из `C:\Work` (структура: `\Библиотека\объект.sru`) |
| **Export_Main_PB** | Указан в bat/ps1 | Выгруженные тексты объектов PB из `C:\SRC125` (аналогичная структура) |
| **Export_Current_BD** | Указан в bat/ps1 | Выгруженные DDL-скрипты из БД Current (структура: `\БД\Тип_объекта\объект.sql`) |
| **Export_Main_BD** | Указан в bat/ps1 | Выгруженные DDL-скрипты из БД Main |
| **Папка Task** | `C:\AIS\1 Release\<JIRA-код>` | Рабочие материалы по задаче. Имя папки совпадает с номером задачи (например, `SYBASE-19337` или `SYBASE-19337__19242`). |
| **Папки Ready** | `C:\AIS\1 Release\<Task>\Ready_ГГГГ_ММ_ДД` | Подготовленные к тестированию/выпуску объекты. Файлы `.sql` – объекты БД, остальные – объекты PowerBuilder. |

---
Значение физического расположения должно задаваться в настроечном файле или позволять менять в диалоговом окне данные из настроечного файла.  Новые данный должны сохраняться в настроечном файле. Должен вестись архив изменений.

### Методика проверки

Проверка пригодности объектов к выводу в промышленную эксплуатацию базируется на трёх принципах:

1. **Актуальность экспорта** – все четыре набора выгруженных объектов (`Export_Current_PB`, `Export_Main_PB`, `Export_Current_BD`, `Export_Main_BD`) должны быть обновлены непосредственно перед проверкой.
2. **Единый эталонный набор из Ready** – из всех существующих папок `Ready_*` формируется сводная выборка, где при совпадении имён объектов остаётся только самый свежий (по дате изменения файла).
3. **Трёхстороннее сравнение** – каждый объект из сводного набора сравнивается с соответствующим объектом в `Export_Current` (должен совпадать) и с объектом в `Export_Main` (должен отличаться). Для объектов PowerBuilder дополнительно проверяется состояние Check Out в VSS на пользователя User.

Только при одновременном выполнении всех условий объект считается готовым к переносу в ПРОД.

---

### План подготовки и проверки

#### Этап 1. Обновление выгруженных представлений

1. Запустите **bat/ps1-скрипты**, обновляющие экспорт из папок `Current` и `Main` (PowerBuilder), дождитесь завершения.
  Скрипт для обновления объектов в папке Main : C:\AIS\AI\Prod\Export.bat  C:\SRC125\gold C:\AIS\AI\Prod\PB_Main gold 
  Скрипт для обновления объектов в папке Current : C:\AIS\AI\Prod\Export.bat  C:\Work\gold C:\AIS\AI\Prod\PB_Current gold 
2. Запустите **bat/ps1-скрипты**, выгружающие SQL-объекты из **БД Current** и **БД Main**, дождитесь завершения.
  Создать бат файл для выгрузки SQL объекта, в который в качестве параметра передавались тип объекта, его имя, имя сервера и имя базы данных.  Бат файл создать по подобию файла - SQL_exp_param.bat
3. Убедитесь, что в папках `Export_Current_PB`, `Export_Main_PB`, `Export_Current_BD`, `Export_Main_BD` присутствуют актуальные файлы, время модификации соответствует времени запуска.

#### Этап 2. Формирование сводного набора объектов из папок Ready

1. Перейдите в папку `C:\AIS\1 Release\<Task>` (например, `SYBASE-19337__19242`).
2. Найдите все подпапки с префиксом `Ready_`.
3. Создайте временную рабочую папку, например, `C:\Temp\ReadyMerged\<Task>`.
4. Для **каждого** файла из всех найденных `Ready_*` подпапок:
   - Если в целевой папке `ReadyMerged` файла с таким относительным путём ещё нет – скопируйте его.
   - Если файл уже существует – замените его **только в том случае**, если дата изменения копируемого файла новее уже находящегося в целевой папке.
   - Структуру подпапок внутри `Ready_*` сохраняйте (для объектов PB она обычно повторяет библиотечное дерево, для SQL – схему БД и тип объекта).

Результат: в `C:\Temp\ReadyMerged\<Task>` лежит единый набор **самых свежих** версий объектов, подготовленных к выпуску.

#### Этап 3. Проверка объектов PowerBuilder (все файлы, кроме `*.sql`)

Для каждого файла из `ReadyMerged` (рекурсивно), чьё расширение не равно `.sql`, выполните следующие шаги.

##### 3.1. Сравнение с Export_Current_PB

- Найдите соответствующий файл в `Export_Current_PB` по совпадению относительного пути (имя библиотеки / имя объекта с расширением `.sru` или `.srw` и т.п.).
- Выполните побайтовое сравнение содержимого (например, командой `fc /B` в командной строке или с помощью утилиты diff).
- **Критерий:** содержимое должно быть **идентичным**.
- При несовпадении – объект **не готов**, зафиксируйте расхождение и переходите к следующему файлу.

##### 3.2. Сравнение с Export_Main_PB

- Найдите тот же объект в `Export_Main_PB`.
- Сравните содержимое.
- **Критерий:** содержимое должно **отличаться**.
- Если содержимое совпадает – изменения отсутствуют, объект **не должен** выводиться в ПРОД (либо требуется уточнить необходимость переноса).

##### 3.3. Проверка состояния в VSS (SourceSafe)

- Откройте клиент VSS, подключитесь к соответствующей базе.
- Найдите файл проекта, соответствующий проверяемому объекту (ориентируясь на путь внутри `$/...`).
- Убедитесь, что статус файла – **Check Out** (значок с красной галочкой).
- Откройте свойства файла (`File → Properties → Check Out Status` или `SCC Properties` → вкладка `Check Out Status`).
- Убедитесь, что в поле **User** указан именно **User** (пользователь, выполняющий проверку).
- **Критерий:** файл взят на изменение пользователем User.

Если хотя бы одно из трёх сравнений/проверок дало отрицательный результат, объект не может быть допущен к выводу в ПРОД без дополнительного анализа.

#### Этап 4. Проверка объектов SQL (файлы `*.sql`)

Для каждого `.sql` файла из `ReadyMerged`:

1. Восстановите полный путь объекта внутри БД. Структура обычно: `\Имя_БД\Тип_объекта\имя_объекта.sql` (например, `B\procedures\my_proc.sql`).
2. Найдите соответствующий файл в `Export_Current_BD`, сравните содержимое.
   - **Критерий:** содержимое **совпадает**.
3. Найдите соответствующий файл в `Export_Main_BD`, сравните содержимое.
   - **Критерий:** содержимое **отличается**.
4. При несовпадении с Current или при совпадении с Main – объект **не готов**.

#### Этап 5. Оформление результатов проверки

1. Подготовьте отчёт (таблицу) со списком всех проверенных объектов, итогом по каждому (готов / не готов) и причиной неготовности.
2. Если все объекты удовлетворяют критериям, набор считается проверенным и может быть передан на установку в промышленную среду.
3. При наличии расхождений:
   - Для несовпадений с `Export_Current` – требуется повторная выгрузка объектов из папки `Current` / БД Current и обновление файлов в `Ready`.
   - Для совпадений с `Export_Main` – уточнить у разработчика/аналитика необходимость переноса данного объекта.
   - Для отсутствия Check Out на User – проверить, кто реально забрал объект, и при необходимости перевести его на User.

---

### Примечания

- Все bat/ps1-скрипты, упомянутые в этапе 1, должны быть заранее настроены и проверены. Адреса выходных папок зафиксированы в самих скриптах.
- Если в папках `Ready_*` встречаются объекты, имена которых дублируются в разных подпапках, приоритет всегда отдаётся **более поздней дате изменения файла**.
- Проверка VSS выполняется вручную через интерфейс SourceSafe – автоматизировать её без дополнительных инструментов затруднительно.
- Рекомендуется перед массовым выпуском выполнять проверку на одном-двух объектах для подтверждения корректности всего конвейера.
 - Создать отчет о результатах работы в виде файла и в виде отображаемой на экране таблицы.
 - Предоставить возможность сравнения скрипта выводимых и исходных  объектов.  Для сравнения использовать сервис программы TortoiseMerge.exe, но в настроечных файлах предоставить возможность изменения сервиса на другую программу.
 - При подтверждении об удачной проверки и получении разрешения - записать в JIRA в комментариях таблицу с перечнем выводимых объектов.  Пример таблицы :
|Проект/Сервер|Библиотека/БД|Наименование объекта|Информация|
|DEV_GOLDEN|golden|fn_reestr_type_id|Добавили условия для определения типа реестра = 12.|
|DEV_GOLDEN|golden|usp_ecp_report_diadoc|Добавил обработку типа реестра = 12|
|DEV_GOLDEN|golden|usp_mis_request_ins_auto|Добавил обработку типа реестра = 12|
|АИС|golden_commission|u_report_list|При нажатии кнопки "Выполнить"  комментарий про тип реестра/запроса для лога берет из поля reestr_comment  таблицы ais_cat_reestr_type по указанному типу|

, где для объектов PowerBulder указывать данные в следующем порядке : проект( в нашем случае  - это AIS ), Наименование библиотеки ( в нашем случае это имя PBL файла или имя папки, где находится выгруженный объект ), Наименование объекта, Информация ( краткий комментарий о сути изменений ).
Для объектов SQL  указывать данные в следующем порядке : Сервер, БД, Наименование объекта ( SQL ), Информация ( краткий комментарий о сути изменений ).
